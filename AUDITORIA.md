RLS (Row Level Security) desligadoAltoBanco de Dados (Supabase)Ligar o RLS na tabela produtos e criar policies estritas para impedir que utilizadores anónimos apaguem ou alterem o stock diretamente.2. Validações críticas rodando apenas no clienteAltoapp/page.tsx (linhas 36-41)Mover a verificação de campos vazios e de valores negativos para o servidor (usando Next.js Server Actions), pois atualmente um utilizador mal-intencionado pode contornar a interface e inserir preços negativos enviando a requisição direta.3. Mistura de responsabilidades (UI e Dados)Médioapp/page.tsx (todo o ficheiro)Separar a lógica de acesso ao Supabase para ficheiros dedicados (camada de dados), deixando a página apenas com a renderização da interface e eventos (UI).4. Ausência total de testes de integraçãoMédioTodo o projetoConfigurar um ambiente de testes local (ex: Jest ou Playwright) com um banco de dados separado para validar as operações de criação, leitura, atualização e eliminação do stock.5. Exposição da chave anónima do SupabaseBaixo.env.local e app/page.tsx (linha 7-8)A chave anónima é pública por design e está na variável NEXT_PUBLIC_, mas sem o RLS ativado (Achado 1), ela torna-se uma vulnerabilidade grave. A correção imediata do Achado 1 mitiga este risco.1. Testes de Integração:
Não existe ferramenta de teste configurada, nem base de dados separada para testes. Não existem testes a validar os fluxos críticos de registo e exclusão de produtos.2. Confiança no Cliente:
As regras que bloqueiam preços negativos e quantidades em falta residem unicamente no front-end. As chaves do Supabase estão expostas no cliente (o que é o padrão com NEXT_PUBLIC_), mas como a tabela não possui Políticas de Segurança (RLS), o banco está totalmente aberto.3. Race Condition:
Não verificado de forma grave no estado atual, pois o CRUD apenas insere novos registos em vez de subtrair unidades existentes de um stock (o que causaria problemas se duas requisições de baixa chegassem ao mesmo tempo).4. Idempotência:
Não verificado. O sistema ainda não possui integrações com webhooks ou gateways externos de pagamento.5. Separação de Responsabilidades:
O ficheiro app/page.tsx é o candidato número 1 para refatoração, pois intercala a camada de visualização em HTML com as chamadas diretas à API do Supabase.
